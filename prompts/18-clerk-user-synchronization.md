# 18 · Clerk user synchronization

Status: approved

## Goal
Synchronize each authenticated Clerk session in the Expo app with the existing Laravel User model in PostgreSQL. Create or refresh the same local user by verified Clerk ID on repeated sign-ins without trusting client-supplied identity or profile fields.

## Decisions
- Preserve the existing Clerk application, provider, token cache, and password, email-code, and social sign-in flows. Clerk remains responsible for authentication; Laravel owns local user data and application authorization.
- Add `POST /api/auth/sync` with no profile payload. Expo sends the current Clerk session token as an Authorization bearer token. Return a minimal local user representation under `data` on success.
- Verify the signature with the configured instance's public key, pin RS256, and validate issuer, expiry, not-before, issued-at, subject, session ID, and active session status where present. Validate `azp` against configured allowed origins when present; native tokens may omit it. Do not derive trusted keys or network destinations from unverified token claims.
- Propose adding `firebase/php-jwt` as the only backend dependency, using a current PHP-compatible release verified against its documentation at implementation time. This replaces handwritten JWT cryptography. Approval of this plan includes this dependency change.
- Keep the Clerk public key, issuer, authorized parties, and Backend API secret in Laravel configuration backed by environment variables. Never expose the secret to Expo, log tokens, or commit credentials. Use the existing Clerk instance and explicitly document required configuration in example environment files.
- After token verification, fetch `/v1/users/{verified_subject}` from Clerk's fixed Backend API using Laravel's HTTP client and the server secret. Require the returned ID to match. Read only the primary email, first name, last name, and image URL; validate shape and storage lengths before persistence. Do not accept these values from the mobile request or use client-writable metadata for authorization.
- Add a new migration, preserving existing migrations and records: unique nullable `clerk_id` for legacy compatibility, nullable `first_name`, `last_name`, and `profile_image_url`, and nullable password. Preserve existing `name` as a derived display value for compatibility. Allow a missing primary email by making email nullable while retaining its unique constraint. Do not create placeholder passwords or email addresses.
- Keep the email unique constraint and never associate existing users by email. Return a safe 409 conflict for an email already owned by another local record; leave both records unchanged. Legacy account linking requires a separate explicit workflow.
- Use the existing User model and Eloquent's database-conflict-safe upsert keyed by the unique `clerk_id`, then read the resulting user. Allow nullable profile values to clear previous values. Avoid overwriting application authorization fields. Do not store Clerk tokens or create Sanctum tokens.
- Use a small token-verification middleware/helper, a controller, and a minimal response resource if appropriate to established conventions. No repository or generic identity abstraction.
- Mount a central synchronization component beneath ClerkProvider, triggered by a loaded signed-in session ID rather than individual sign-in buttons. Include restored sessions and sign-up-created sessions. Deduplicate in-flight work, reset on sign-out/session change, and prevent stale requests from affecting a different user's UI.
- Use a separate typed request function with a fresh `getToken()` call per attempt, a timeout, cancellation, and a small bounded retry for network/429/5xx failures. Treat this as a transient synchronization operation; do not introduce a server-state cache solely to retain the returned profile. If implementation introduces retained server state, use TanStack Query per mobile instructions.
- Display a short loading/error state with explicit retry and sign-out on synchronization failure. Keep signed-out guest browsing available; signed-in content resumes after synchronization succeeds. Do not report Clerk sign-in itself as failed when Laravel synchronization fails.
- No live database writes, account creation, account linking, or production deployment during verification without authorization. Use isolated test data and clearly report any manual sign-in/configuration checks still required.

## Out of scope
Webhooks, background profile synchronization, Clerk user deletion handling, legacy account migration, role systems, authorization policies for future domain endpoints, listing API integration, removal of Sanctum, additional infrastructure, and unrelated UI changes.
